# Quality control of a property exposure file before modelling: rules, repairs and what they cannot see

How much damage can a messy location file do before a catastrophe model sees it, and how much of it can a rule-based pass catch and repair? A synthetic commercial property portfolio for Germany in an OED-like layout is corrupted with defects of known type and number, a rule set flags them, unambiguous cases are repaired, and the effect on total insured value and on accumulation is measured.

**What is real and what is simulated.** Real: the 10,815 German postcode centroids of GeoNames (CC BY 4.0), used to place the locations. Simulated: everything else (8,000 locations, 120 accounts, values from lognormal distributions, floor areas, construction and occupancy). The code lists are short assumed lists, not the official OED tables, and the field names follow OED only in spirit. **No client data, no claims data.** The defects were designed by me together with the rules, so the detection rates below measure whether the rules do what they were written to do, not how they would perform on a real broker file.

## Results (`results/summary.json`, `results/detection_by_defect.csv`)
- **Defects injected: 1,224** in 8,160 rows (8,000 locations plus 160 duplicate copies), one defect per row: missing coordinates 160, swapped latitude and longitude 80, coordinates far from the postcode (more than 25 km) 160, invalid postcode 80, values scaled by 1000 in either direction 80, non-positive value 40, duplicates 160, year built invalid 80, storeys invalid 64, unknown construction or occupancy code 120, wrong currency 40, total insured value not equal to its parts 80, character encoding damage in the place name 80.
- **Detection by the rules: 1,221 of 1,224 injected defects (recall 0.998), precision 0.995 (rule flags that match an injected defect).** Misses: two of the 160 locations moved to another place (the random new position fell within 25 km of the postcode centroid) and one duplicate whose value differed by more than 5%. Eight of the 8,000 clean rows were flagged: six because the GeoNames file itself contains place names with damaged encoding (for example `KrankenhÃ¤user des MÃ¤rkischen Kreises GmbH` in the city field; a real defect of the source, found by the encoding rule) and two by the peer-outlier rule.
- **Effect on exposure.** The clean file holds 30.67 billion EUR. The corrupted file reads 207.2 billion (6.8 times), because a few locations with values multiplied by 1000 dominate; the largest half-degree cell holds 9.8% of the total value in the raw file against 2.7% in the clean one (20.2 against 0.82 billion EUR). After repairs (swapped coordinates, unit errors, encoding, sum of parts) and removal of the 637 rows that cannot be modelled as they are (blocking rules and duplicates, 7.8% of rows) the total is 28.8 billion EUR, 94.0% of the clean value, and the largest cell is 0.79 billion (2.7%). The 6% of value lost is the clean locations with missing or doubtful coordinates, wrong currency or postcode; they would have to be returned to the client.
- **What the rules do not see (`not_covered_by_rules`).** Coordinates shifted by 15 km (inside the postcode tolerance): 0 of 160 found; a valid but wrong construction code: 0 of 160; value multiplied by 3: 160 of 160, but only after I added a peer rule (robust z-score of value per square metre within occupancy and construction, threshold 4) because the first run found 1 of 160. That rule was written after seeing the failure, so its result is not an out-of-sample test. Errors inside the tolerance of a rule remain in the file and still move the modelled loss; the postcode tolerance of 25 km is a trade-off between false alarms and misses.

## Method
Rules (`src/edq/validate.py`): missing or out-of-country coordinates, swapped latitude and longitude, distance to the nearest centroid of the stated postcode, postcode format and existence, non-positive value, value per square metre outside 150 to 20,000 EUR and against peers, duplicates by address and postcode with values within 5%, year built outside 1700 to 2026, storeys outside 1 to 60, unknown codes, currency other than EUR, value not equal to the sum of its parts (2% tolerance), encoding damage. Each rule has a severity: block (cannot be modelled), fix (repaired when unambiguous), warn (check). Repairs are applied only where one repair is correct: swap, factor 1000, encoding, recomputed sum.

## What this does not show
No real file, no OED validation against the official schema and code tables, no geocoding service (the check uses postcode centroids, which can be far from a valid address inside a large postcode area), no claims or policy data, no check of values against replacement cost beyond the per-square-metre bands, and no effect on a modelled loss, only on total value and accumulation. The detection results hold for defects I defined; real files have defects nobody has listed.
